# Scalability

## NFR-S1 — Concurrency bounded by CPU work, not by memory

| Requirement | Statement |
|---|---|
| NFR-S1.1 | The service **MUST** apply backpressure when in-flight CPU work exceeds available capacity, rather than queueing unboundedly. |
| NFR-S1.2 | Queued request bodies **MUST** be bounded by count **and** by total bytes. |
| NFR-S1.3 | `GET /v1/runs/{run_id}` **MUST NOT** be blocked by `POST /v1/runs` load. |

NFR-S1.3 matters because of the service's cost asymmetry. A run retrieval is a single store read;
a run submission is up to 50 million comparisons
([measured](/design/step-counting-semantics.md#consequence-2--bubble-sorts-worst-case-is-exactly-nn12)).
A shared worker pool with a uniform concurrency limit means a burst of expensive submissions
makes cheap retrievals slow — which is backwards, and disproportionately hurts
[US-7](/requirements/user-stories.md), where the whole point is handing a student a `run_id` to
fetch.

Phase 1's answer is separate limits per route class, not a queue.

### The CPU-bound consequence

Because every run's cost is [bubble sort's quadratic cost](/algorithms/bubble-sort.md), the
service is **CPU-bound**. Adding concurrency does not add throughput on one core; it adds
context switching and memory pressure. Throughput scales with cores and instances, and only
with those. This is worth stating because the intuition from typical IO-bound services — "it is
async, so it scales" — is wrong here.

## NFR-S2 — Horizontal scaling of the API tier

| Requirement | Statement |
|---|---|
| NFR-S2.1 | The API tier **MUST** be stateless with respect to run data. |
| NFR-S2.2 | Any instance **MUST** be able to serve a retrieval for a run created by any other instance. |
| NFR-S2.3 | `run_id` generation **MUST NOT** depend on instance-local state. |

These hold by construction in phase 1: `run_id` is generated by the service and results are
written to the shared store before the response is sent
([request lifecycle](/architecture/request-lifecycle.md#step-6--persist-before-responding)).
The persist-before-respond ordering is what makes NFR-S2.2 true; reversing it would introduce a
window in which a valid `run_id` is unretrievable.

Algorithm registration is compile-time
([registry](/design/algorithm-registry.md#why-algorithms-are-compiled-in-not-uploaded)), so all
instances necessarily agree on the registry — no coordination needed, and no chance of skew.

### The constraint on scaling

Scaling out does **not** help a single oversized request. One n = 10,000 request consumes about
as much CPU as a thousand small ones. Past a point the service is limited by aggregate CPU
rather than by per-request latency, and no architecture fixes that while bubble sort is
registered at an input limit sized for it.

The real lever is the [input limit](/design/input-validation.md), not horizontal scaling.

## NFR-S3 — Store growth and retention: unspecified

**This requirement is deliberately left unspecified.** No request volume has been stated, so
any retention period or capacity figure would be invented
([NFR overview](/nfr/nfr-overview.md#what-is-missing-and-honestly-so)).

What *is* specified is the shape of the problem:

| Property | Value |
|---|---|
| Entities stored | One `Run` per submission, each containing `input` and `results[]` |
| Growth driver | `input` inline — up to 10,000 integers per run |
| Write pattern | Write-once, never updated, never deleted in phase 1 |
| Read pattern | Key lookup only; **no scans or listing** in phase 1 ([scope](/requirements/scope-and-phasing.md)) |
| Dominant cost | Storage volume, not query complexity — there are no queries |

Storing `input` inline means storage grows with `10,000 × submissions`, which will outgrow a
document store's comfortable working set long before anything else becomes a problem. The
documented mitigation is in
[the data model](/architecture/data-model.md#on-storing-input): keep the `Run` shell plus pointers
in the primary store and move `input` and `results[]` to object storage.

Deliberately **not** specified yet: retention period, storage tiering, or archival.

## NFR-S4 — Cost behaviour is predictable

| Requirement | Statement |
|---|---|
| NFR-S4.1 | Cost per run **MUST** be bounded by the [input limit](/design/input-validation.md) and the [time budget](/nfr/reliability.md#nfr-r2--per-run-time-budget-enforced), not left open. |
| NFR-S4.2 | A caller **MUST** be able to reduce cost by selecting a subset of algorithms ([FR-3](/requirements/functional-requirements.md)). |

NFR-S4.2 is the only cost lever a caller has in phase 1, and it is a real one: omitting bubble
sort removes essentially the whole cost of a run. It is exposed in the API rather than
mentioned only in prose.

## What is deliberately not designed for

* **Multi-tenancy.** No tenant concept exists because there are no identities
  ([security](/nfr/security.md)).
* **Cross-region distribution.** Nothing requires it, and it would add latency to the one
  operation that must be right.
* **Sharding.** Key-lookup access to a write-once store does not need it at any volume this
  service is plausibly headed for. Revisit if a listing endpoint is ever added, which is the
  point at which scans — and therefore sharding questions — arrive.
